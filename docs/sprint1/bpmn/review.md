# Протокол рецензування BPMN-моделей

**Продукт:** П4 «СтейНау» · **Спринт:** 1 · **Дата:** 27.09.2026 · **Автор моделей:** Інженер з тестування
---

Кожну модель перевіряє рецензент, який її не будував (Тест-аналітик або Скрам-майстер),
за чек-листом коректності BPMN із 10 пунктів. Модель вважається такою, що пройшла
рецензування, коли виконано всі десять пунктів.

## Чек-лист (10 пунктів)

| № | Пункт |
|---|---|
| 1 | У кожному пулі з власним процесом є ≥1 початкова і ≥1 кінцева подія; початкова має лише вихідні потоки, кінцева — лише вхідні |
| 2 | Кожна дія має ≥1 вхідний і ≥1 вихідний потік управління; «висячих» елементів немає |
| 3 | Потоки управління не перетинають межі пулів; між пулами — лише потоки повідомлень з відправником і одержувачем |
| 4 | Шлюзи-розгалуження XOR/OR підписано питанням, гілки мають умови; умови взаємовиключні або є гілка за замовчуванням |
| 5 | Розгалуження AND та OR закрито синхронізуючим шлюзом того самого типу або кожна гілка має власну кінцеву подію |
| 6 | Після шлюзу за подіями стоять лише проміжні події, а не дії з умовами |
| 7 | Дії названо дієсловом з об'єктом, події — фактом або станом, шлюзи — питанням |
| 8 | Кожна доріжка має назву ролі з легенди і містить ≥1 дію; жодна дія не лежить поза доріжками |
| 9 | Артефакти приєднано асоціаціями, а не потоками управління; об'єкти даних названо іменниками |
| 10 | Модель читається зліва направо без зайвих перетинів; учасники, кроки й результати відповідають опису процесу в легенді |

## Результати рецензування

### 01 — Бронювання номера

**Рецензент:** Валюх Артем · **Дата:** 27.09.2026

| Пункт | Так / ні | Зауваження | Виправлено (коміт) |
|---|---|---|---|
| 1 | Ні | У пулі «Готель» відсутня початкова подія. Процес починається безпосередньо із задачі «Перевірити формат полів». |  |
| 2 | Ні | Задача «Перевірити формат полів» не має вхідного потоку управління; до неї надходить лише потік повідомлення від гостя. |  |
| 3 | Так | Потоки управління залишаються в межах пулів, а взаємодія між гостем і готелем виконана потоками повідомлень. |  |
| 4 | Так | XOR-шлюзи «Дані коректні?» та «Номер вільний?» сформульовані як питання, гілки позначені «так» / «ні». |  |
| 5 | Так | Розгалуження AND та OR у моделі відсутні. |  |
| 6 | Так | Після шлюзу за подіями «Яка відповідь системи?» розташовані проміжні події-повідомлення. |  |
| 7 | Ні | Кінцеві події «Відмовити: дані некоректні» та «Відмовити: номер зайнятий» названі як дії, а не як факт або стан. |  |
| 8 | Так | Доріжки «Система» та «Адміністратор готелю» відповідають ролям продукту та містять дії. |  |
| 9 | Ні | Об'єкт даних «Бронювання» приєднано лише до задачі «Створити бронювання», хоча за таблицею елементів він також має бути пов'язаний із надсиланням підтвердження гостю. |  |
| 10 | Ні | Початкова подія гостя «Потребу в номері визначено» не відображає тригер із product.md: гість обрав номер і натиснув «Бронювати». |  |

### 02 — Заселення і виселення

**Рецензент:** Валюх Артем · **Дата:** 27.09.2026

| Пункт | Так / ні | Зауваження | Виправлено (коміт) |
|---|---|---|---|
| 1 | Так | У пулах «Гість», «Готель» і «Служба прибирання» присутні початкові та кінцеві події. |  |
| 2 | Так | Дії включені в потік управління, висячих задач не виявлено. |  |
| 3 | Так | Між пулами використовуються потоки повідомлень: прибуття гостя, видача ключа, виїзд і взаємодія зі службою прибирання. |  |
| 4 | Так | XOR/OR-шлюзи у моделі відсутні; шлюз за подіями використано для очікування прибуття гостя або завершення часу очікування. |  |
| 5 | Так | Паралельне AND-розгалуження «Розпочати завершальні дії» закрите AND-шлюзом перед продовженням процесу. |  |
| 6 | Так | Після шлюзу за подіями розміщені лише проміжна подія-повідомлення та проміжна подія-таймер. |  |
| 7 | Ні | AND-шлюзи названі «Розпочати завершальні дії» та «Завершити завершальні дії», тоді як чек-лист вимагає називати шлюзи питаннями. |  |
| 8 | Так | Доріжки «Адміністратор готелю» і «Менеджер», а також пули гостя та служби прибирання відповідають ролям легенди. |  |
| 9 | Ні | Об'єкт даних «Бронювання» має асоціацію лише із задачею «Знайти бронювання», хоча в product.md передбачені також асоціації до «Встановити статус "Заселено"» і «Закрити бронювання». |  |
| 10 | Так | Загальний порядок заселення, проживання, виселення та прибирання відповідає опису процесу в product.md. |  |

### 03 — Скасування і повернення коштів

**Рецензент:** Валюх Артем · **Дата:** 27.09.2026

| Пункт | Так / ні | Зауваження | Виправлено (коміт) |
|---|---|---|---|
| 1 | Ні | У пулі «Готель» немає початкової події; процес починається безпосередньо із задачі «Визначити кількість днів до заїзду». |  |
| 2 | Ні | Перша задача пулу «Готель» не має вхідного потоку управління та отримує лише повідомлення «Запит на скасування». |  |
| 3 | Так | Взаємодія між гостем, готелем і платіжним провайдером виконана потоками повідомлень; sequence flow межі пулів не перетинає. |  |
| 4 | Так | XOR-шлюзи сформульовані як питання, а вихідні гілки позначені відповідними варіантами. Точні межі рівнів штрафу свідомо не зафіксовані через суперечність F-110 і BL-60. |  |
| 5 | Так | AND та OR-розгалуження у моделі відсутні. |  |
| 6 | Так | Шлюз за подіями у цій моделі не використовується. |  |
| 7 | Так | Дії названо дієсловами, події — фактами або станами, XOR-шлюзи — питаннями. |  |
| 8 | Так | Доріжки «Система» та «Менеджер» і пул «Платіжний провайдер» відповідають ролям легенди. |  |
| 9 | Ні | Об'єкт даних «Бронювання» пов'язано із задачею «Звільнити номер», але відсутня передбачена product.md асоціація до задачі «Визначити кількість днів до заїзду». |  |
| 10 | Ні | Після «Показати суму до повернення» у пулі «Готель» sequence flow одразу переходить до «Звільнити номер», тому модель не очікує підтвердження скасування від гостя, хоча за описом процесу номер має звільнятися лише після підтвердження. |  |

### 04 — Обробка повідомлень гостей

**Рецензент:** Валюх Артем · **Дата:** 27.09.2026

| Пункт | Так / ні | Зауваження | Виправлено (коміт) |
|---|---|---|---|
| 1 | Так | У пулах «Гість» і «Готель» наявні початкові й кінцеві події; процес готелю починається Message Start Event «Отримано повідомлення гостя». |  |
| 2 | Так | Основні дії включені в sequence flow; висячих задач не виявлено. |  |
| 3 | Так | Між гостем і готелем використовуються лише потоки повідомлень «Звернення гостя» та «Відповідь на звернення». |  |
| 4 | Так | XOR-шлюз «Який тип питання?» сформульований як питання, а гілки розділені на «ціни або повернення» та «інші питання». |  |
| 5 | Так | AND та OR-розгалуження у моделі відсутні. |  |
| 6 | Так | Шлюз за подіями у моделі не використовується. |  |
| 7 | Так | Дії названі дієсловами, події — фактами або станами, XOR-шлюз — питанням. |  |
| 8 | Так | Доріжки «Система», «Адміністратор готелю» та «Менеджер» відповідають ролям продукту і містять дії. |  |
| 9 | Ні | Для сховища «Повідомлення» відсутня асоціація до задачі «Позначити повідомлення обробленим», а для об'єкта «Звернення гостя» — асоціація до задачі менеджера «Підготувати відповідь», хоча обидві вказані в product.md. |  |
| 10 | Ні | Boundary Timer «Минуло 24 години без відповіді» реалізовано як переривальну подію, тоді як у product.md вона визначена як непереривальна: нагадування має виконуватись паралельно і не припиняти підготовку відповіді менеджером. |  |
